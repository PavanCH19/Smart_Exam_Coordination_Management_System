that needs to be built. It was generated by reading every API call the frontend makes
(`src/axiosRoutes/*.js`) and every field each form/page reads or sends. If the backend
implements exactly what's described here, the frontend should work with **no changes**.

## 1. Conventions

**Base URL.** The frontend reads `VITE_API_BASE_URL` from `.env`, currently:
```
VITE_API_BASE_URL=http://localhost:5000/api/v1
```
Every path below is **relative to that base**. e.g. `GET /students` really means
`GET http://localhost:5000/api/v1/students`.

**Auth header.** Every request automatically carries:
```
Authorization: Bearer <accessToken>
```
(`src/axiosRoutes/axiosConfig.js` reads `accessToken` from `localStorage` and attaches it via
an axios interceptor. No endpoint needs to be told about this — just validate the JWT.)

**Content type.** `application/json` for all requests, except:
- Bulk student upload (`multipart/form-data`, see [§6](#6-file-upload--download-notes))
- Any `download`/`export` endpoint, which the frontend requests with `responseType: 'blob'`
  and expects a raw file body (PDF/CSV), not JSON.

**Standard success envelope.** Every JSON response is expected in this shape:
```json
{
  "data": /* object or array — the actual payload */,
  "pagination": { "page": 1, "limit": 10, "total": 42, "totalPages": 5 },
  "message": "optional human-readable string"
}
```
- `pagination` is only expected on **list** endpoints that support paging (see each endpoint).
- The frontend reads `response.data.data` first, and falls back to `response.data` if `data`
  is absent — so wrapping in `data` is preferred but not fatal. **Always** wrap paginated
  responses this way so `response.data.pagination` is present.

**IDs.** The frontend treats every `*_id` field as an opaque string/number and never parses it
— use whatever your database's native primary key type is (auto-increment int, UUID, etc.),
just be consistent. The one exception is **students**, which are looked up by **`usn`** for
update/delete (not `student_id`) — see [§5.4](#54-students).

**Dates & times.** Send `exam_date` as an ISO date string (`"2026-11-04"` or a full ISO
datetime — the frontend slices the first 10 characters). Send `start_time` / `end_time` as
`"HH:MM"` 24-hour strings (matches native `<input type="time">`).

**Pagination query params.** List endpoints are called with `?page=<n>&limit=<n>` plus
whatever filters are documented per-endpoint.

## 2. Authentication

- JWT bearer tokens, issued at login, sent on every subsequent request.
- Passwords hashed with bcrypt (or equivalent) server-side.
- Role-based access control: every route below is tagged with which role(s) may call it.
  `ADMIN` routes must reject `STAFF`/`STUDENT` tokens (403), and vice versa for
  role-scoped "my ..." endpoints.
- The frontend decides which dashboard to redirect to after login purely from
  `user.role` (`ADMIN` → `/admin/dashboard`, `STAFF` → `/staff/dashboard`,
  `STUDENT` → `/student/dashboard`), so `role` **must** be one of exactly those three
  uppercase strings in the login response.
- `user.student_id` is required on the login response **for STUDENT accounts** — several
  student-portal pages (`Timetable`, `Venue & Seat`) call `getStudentExams(user.student_id)`
  using this field directly from the stored auth state.

## 3. Database schema reference

This consolidates the tables implied by the whole frontend (superset of the tables listed in
the original project brief, extended with everything the UI actually needs).

```
departments
  department_id   PK
  name            string, unique
  code            string, unique (e.g. "CSE")
  description     text, nullable

courses
  course_id       PK
  name            string
  code            string (e.g. "BE CSE")
  department      string (FK -> departments.name, or department_id — see note below)
  duration_years  int
  total_semesters int

subjects
  subject_id      PK
  subject_code    string, unique
  subject_name    string
  department      string
  semester        int (1-8)
  duration        int (minutes — used as default exam duration)

rooms
  room_id         PK
  room_number     string, unique
  building        string
  floor           int
  capacity        int
  room_type       enum: Classroom | Hall | Laboratory | Auditorium | Seminar Hall
  status          enum: AVAILABLE | UNAVAILABLE | MAINTENANCE

students
  student_id      PK
  usn             string, unique   -- primary lookup key for update/delete!
  name            string
  email           string
  phone           string
  department      string
  semester        int
  section         enum: A | B | C | D
  course          string

staff
  employee_id     PK (string, human-assigned e.g. "EMP001")
  name            string
  department      string
  email           string
  phone           string
  designation     string
  availability    enum: AVAILABLE | UNAVAILABLE

users                              -- separate from students/staff: login credentials
  user_id         PK
  name            string
  email           string, unique
  password_hash   string
  role            enum: ADMIN | STAFF | STUDENT
  status          enum: ACTIVE | INACTIVE
  student_id      FK -> students.student_id, nullable (set when role = STUDENT)
  employee_id     FK -> staff.employee_id, nullable (set when role = STAFF)

exams
  exam_id         PK
  subject_id      FK -> subjects.subject_id
  subject_name    string   -- denormalized for convenience, see note below
  subject_code    string   -- denormalized
  department      string
  semester        int
  exam_date       date
  start_time      time ("HH:MM")
  end_time        time ("HH:MM")
  status          enum: SCHEDULED | COMPLETED | CANCELLED

room_allocations
  allocation_id   PK
  exam_id         FK -> exams.exam_id
  room_id         FK -> rooms.room_id
  room_number     string   -- denormalized
  building        string   -- denormalized
  capacity        int      -- denormalized (room's capacity, for display)
  student_count   int      -- students assigned to this room for this exam

staff_duties
  duty_id         PK
  exam_id         FK -> exams.exam_id
  staff_id        FK -> staff.employee_id
  staff_name      string   -- denormalized
  room_id         FK -> rooms.room_id
  room_number     string   -- denormalized
  duty_type       enum: MAIN | STANDBY
  status          enum: ASSIGNED | PRESENT | ABSENT   -- duty attendance, not student attendance

seating
  allocation_id   FK -> room_allocations.allocation_id
  seat_number     string (e.g. "A1", "B4")
  student_id      FK -> students.student_id
  -- composite key (allocation_id, seat_number) or (allocation_id, student_id)

attendance
  exam_id         FK -> exams.exam_id
  student_id      FK -> students.student_id
  room_number     string   -- denormalized (which room the student sat in)
  seat_number     string   -- denormalized
  status          enum: PRESENT | ABSENT | null (not yet marked)
  -- composite key (exam_id, student_id)

admit_cards
  student_id      FK -> students.student_id
  admit_card_status  enum: PENDING | READY
  generated_at    datetime, nullable
  -- PDF itself can be generated on-the-fly at download time or stored on disk/S3

notifications
  notification_id PK
  title           string
  message         text
  audience        enum: ALL | STUDENTS | STAFF
  type            enum: INFO | REMINDER | ALERT
  sent_at         datetime
  created_by      FK -> users.user_id

notification_reads                 -- per-user read state (for STAFF/STUDENT inbox)
  notification_id FK -> notifications.notification_id
  user_id         FK -> users.user_id
  read_at         datetime

issues
  issue_id        PK
  issue_type      enum: STUDENT_PROBLEM | QUESTION_PAPER | INFRASTRUCTURE | INVIGILATOR | OTHER
  description     text
  duty_id         FK -> staff_duties.duty_id, nullable
  room_number     string, nullable  -- denormalized, for admin table display
  reported_by     FK -> users.user_id (or staff.employee_id)
  reported_by_name string  -- denormalized
  status          enum: "OPEN" | "IN PROGRESS" | "RESOLVED"   -- NOTE: space in "IN PROGRESS"
  created_at      datetime

audit_logs
  log_id          PK
  action          string (e.g. "ROOM_CHANGE", "TIMETABLE_GENERATED", "ATTENDANCE_UPDATED")
  performed_by    FK -> users.user_id
  performed_by_name string  -- denormalized
  target          string, nullable (human-readable target, e.g. "Room A-204")
  details         text, nullable
  timestamp       datetime
```

> **Note on `exams.subject_name` / `subject_code` denormalization:** the frontend displays
> subject name/code directly on exam records (tables, timetable, dashboards) without a join
> round-trip. Either denormalize these two columns onto `exams` at write time, or have your
> API layer join `subjects` and shape the response to include them — the frontend doesn't
> care which, as long as the JSON has `subject_name` and `subject_code` on every exam object.
> The same applies to `room_number`/`building`/`staff_name` on allocations and duties.

## 5. Endpoints

### 5.1 Auth

#### `POST /auth/login`
**Auth:** none (public)
**Body:**
```json
{ "email": "admin@college.edu", "password": "••••••••" }
```
**Response:**
```json
{
  "data": {
    "user": {
      "user_id": 1,
      "name": "Dr. Meera Rao",
      "email": "admin@college.edu",
      "role": "ADMIN",
      "student_id": null,
      "employee_id": null
    },
    "accessToken": "eyJhbGciOi..."
  }
}
```
For a `STUDENT` login, `user.student_id` **must** be populated (see [§2](#2-authentication)).
For a `STAFF` login, `user.employee_id` should be populated similarly.

#### `POST /auth/change-password`
**Auth:** ADMIN, STAFF, STUDENT (any logged-in user, changes their own password)
**Body:**
```json
{ "current_password": "old-pass", "new_password": "new-pass-min-8-chars" }
```
**Response:** `{ "message": "Password updated" }` (2xx). Return 400/401 with a `message` if
the current password is wrong.

Distinct from `students`/`staff` profile records — this is login/access management.

| Method | Path | Auth | Notes |

| GET | `/users` | ADMIN | List. Query: `role` (optional filter), `page`, `limit` |

| PUT | `/users/:userId` | ADMIN | Update |
| DELETE | `/users/:userId` | ADMIN | Deactivate/delete |

**List/response item shape:**
```json
{ "user_id": 12, "name": "Priya Nair", "email": "priya@college.edu", "role": "STAFF", "status": "ACTIVE" }
```

### 5.4 Students

| Method | Path | Auth | Notes |
|---|---|---|---|
| GET | `/students` | ADMIN | Paginated list. Query: `page`, `limit`, `search`, `department`, `semester`, `section`, `course` |
| GET | `/students/search` | ADMIN | Same filters as above, used for live search in Staff search box pattern elsewhere — *(students page uses `/students` with filters, not this endpoint, but it's wired up and available)* |
| POST | `/students` | ADMIN | Create |
| PUT | `/students/:studentId` | ADMIN | Update — **`:studentId` here is actually the student's `usn`** (see below) |
| DELETE | `/students/:studentUsn` | ADMIN | Delete by `usn` |
| POST | `/students/bulk-upload` | ADMIN | CSV bulk import — `multipart/form-data`, field name `file`. See [§6](#6-file-upload--download-notes) |
| GET | `/students/:studentId/exams` | ADMIN, STUDENT (self) | A student's exam list (used by admin "view exams" action, and by the student portal's own Timetable/Venue&Seat pages) |
| GET | `/students/:studentId/attendance` | ADMIN | A student's attendance history (admin "view attendance" action) |

> **Important:** `updateStudent` and `deleteStudent` are called with the student's **`usn`**
> as the path parameter, not `student_id`. Route them as `PUT /students/:usn` and
> `DELETE /students/:usn`, or accept either identifier — but the frontend will always send
> the `usn` value in that slot.

**Create/update body:**
```json
{
  "usn": "1XX20CS045",
  "name": "Anika Sharma",
  "email": "anika@college.edu",
  "phone": "9876543210",
  "department": "Computer Science",
  "semester": 5,
  "section": "A",
  "course": "BE CSE"
}
```
`usn` is disabled (read-only) in the edit form, so it's only sent on create.

**List item shape** (also used in `getStudentExams`'s parent context for department/semester
matching by other modules):
```json
{ "student_id": 501, "usn": "1XX20CS045", "name": "Anika Sharma", "email": "...", "phone": "...", "department": "Computer Science", "semester": 5, "section": "A", "course": "BE CSE" }
```

**`GET /students/:studentId/exams` response** — each exam **must** include venue/seat fields
once allocation/seating has run, since the student portal displays them directly:
```json
{
  "data": [
    {
      "exam_id": 101,
      "subject_name": "Database Management Systems",
      "subject_code": "CS301",
      "exam_date": "2026-11-04",
      "start_time": "10:00",
      "end_time": "13:00",
      "status": "SCHEDULED",
      "building": "Main Block",
      "room_number": "A-204",
      "seat_number": "B7"
    }
  ]
}
```

**Bulk upload response:** any shape is fine — the frontend just re-fetches the list after a
successful `2xx`. Return per-row errors in `message` or a `data.errors` array if you want to
surface them (not currently rendered, but harmless to include for future use).

### 5.10 Exams

| Method | Path | Auth |
|---|---|---|
| GET | `/exams` | ADMIN | Query: `page`, `limit`, `status` |
| POST | `/exams` | ADMIN | Create |
| PUT | `/exams/:examId` | ADMIN | Update |


**List item — must include denormalized subject fields:**
```json

  "subject_id": 12,
  "subject_name": "Database Management Systems",
  "subject_code": "CS301",
  "department": "Computer Science",
  "semester": 5,
  "exam_date": "2026-11-04",
  "start_time": "10:00",
  "end_time": "13:00",
  "status": "SCHEDULED"
}
```

**`POST /exams/check-conflicts`** *(optional — graceful client-side fallback exists)*

student/room/staff-level conflict detection later and the frontend route is ready to wire up.


## 6. File upload / download notes

**Bulk student upload** — `POST /students/bulk-upload`
Sent as `multipart/form-data` with a single field:
```
file: <the .csv File object>
```
The frontend's axios interceptor automatically strips the `Content-Type: application/json`
default header whenever the request body is a `FormData` instance, so the browser sets the
correct `multipart/form-data; boundary=...` header itself — no special handling needed beyond
accepting a standard multipart upload. Expected CSV columns match the student create body:
`usn, name, email, phone, department, semester, section, course`.

**All "download" and "export" endpoints** (`admit-cards/:id/download`,
`student/admit-card/download`, `reports/:type/export`) are requested with
`responseType: 'blob'` — respond with the raw file bytes and correct `Content-Type` header
(`application/pdf` or `text/csv`), **not** a JSON envelope. The frontend wraps the blob in an
object URL and triggers a browser download client-side.

## 7. Error response format

Any non-2xx response should include a JSON body with a `message` field — every page reads
`error.response?.data?.message` and displays it directly in an inline error banner:
```json
{ "message": "A room with that number already exists." }
```
Without a `message` field, the frontend falls back to a generic string per-page (e.g. "Failed
to fetch students"), so it degrades gracefully — but a specific `message` gives users (and
admins) much more useful feedback.

**Recommended status codes:**
- `400` — validation errors (missing/invalid fields)
- `401` — missing/invalid/expired token
- `403` — valid token, wrong role for this route
- `404` — resource not found (e.g. no seating generated yet, unknown ID)
- `409` — conflict (e.g. duplicate `usn`, duplicate room number, double-booked staff duty)
- `500` — unexpected server error
